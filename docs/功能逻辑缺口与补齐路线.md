# 功能逻辑缺口与补齐路线

> 日期：2026-06-19  
> 目的：把现有系统从“功能可用”推进到“产品可运营、可计费、可恢复、可排障”。  
> 范围：任务生命周期、计费、幂等、Provider、资产、权限、通知、API、数据一致性与测试。  
> 不覆盖：官网落地页、博客 SEO、视觉设计、品牌文案、产品定位。

## 0. 使用说明

本文档只处理功能逻辑与系统闭环，不和产品蓝图文档重复。

文档里的判断分三类：

- **已确认**：从当前代码结构可以看到的能力。
- **待确认**：需要继续读代码或跑端到端流程才能定论的能力。
- **建议新增**：当前即使已有局部实现，也建议按产品化标准重新定义边界和验收。

后续拆任务时，优先从 P0 开始。P1/P2 不建议抢在 P0 前做大规模实现。

## 1. 当前系统事实

已确认：

- Monorepo 已包含 `apps/client`、`apps/server`、`apps/worker` 与多个领域包。
- 数据层已有统一任务表 `tasks`，状态包含 `queued`、`running`、`retrying`、`succeeded`、`failed`、`cancelled`。
- 已有 `generation_records`、credit ledger、billing policy、Provider health、notifications、SSE、Canvas pipeline、Subtitle、Asset Library、API Keys 等基础模块。
- 后台已有部分 admin routes，例如 tasks、users、providers、api-keys、credit、audit logs。
- 用户端已有 Canvas 资产轮询与 pipeline run 轮询，SSE 失败时有一定兜底。

待确认：

- `generation_records` 与 `tasks`、`canvas_pipeline_runs`、`assets` 的关联是否在所有流程里一致。
- 生成任务从创建、reserve、worker 执行、debit/refund、资产入库、通知的全链路是否全部有测试覆盖。
- 用户侧是否已有可复用的任务 API，只是没有形成统一任务中心。
- Provider health 是否已经参与实际模型路由，而不只是统计展示。
- API Key 是否已有 scope、rate limit profile、last used、revoke 审计等能力。

核心结论：

项目已经具备很多工程基础，但产品级闭环还不完整。下一阶段最重要的不是继续增加模型能力，而是补齐“任务可追踪、费用可解释、失败可恢复、资产可复用、后台可排障”。

## 2. P0：近期必须优先补齐

### 2.1 用户侧统一任务中心

问题：

当前系统已有统一任务表和管理端任务能力，但用户侧还缺一个统一的任务视角。真实用户不会理解 `generation_record`、`pipeline_run`、`canvas_asset`、`subtitle_project` 之间的区别，他只关心：任务是否还在跑、失败原因是什么、钱有没有扣、结果在哪里、能不能重试。

建议新增或整理用户侧任务 API：

```text
GET  /api/tasks
GET  /api/tasks/:id
POST /api/tasks/:id/retry
POST /api/tasks/:id/cancel
```

如果现有路由已经覆盖部分能力，不必重复造接口，但需要对外统一 DTO。

建议 DTO：

```ts
interface UserTaskDTO {
  id: string
  domain: 'generate' | 'canvas' | 'subtitle' | 'gateway'
  type: string
  status: 'queued' | 'running' | 'retrying' | 'succeeded' | 'failed' | 'cancelled'
  title: string
  description: string
  progress: number | null
  currentStep: string | null
  createdAt: string
  updatedAt: string
  finishedAt: string | null
  canRetry: boolean
  canCancel: boolean
  billing: {
    estimatedCents: number | null
    reservedCents: number | null
    actualCents: number | null
    status: 'none' | 'estimated' | 'reserved' | 'debited' | 'refunded' | 'partially_refunded'
  }
  target: {
    type: 'asset' | 'project' | 'subtitle_project' | 'generation_record' | 'external'
    id: string
    href: string
  } | null
  error: {
    code: string
    message: string
    retryable: boolean
    nextAction: 'retry' | 'edit_input' | 'recharge' | 'contact_support' | 'none'
  } | null
}
```

实现要点：

- 用户只能查询自己的任务。
- 管理端 DTO 可以更详细，但不能让用户端直接依赖管理端 DTO。
- `retry` 必须复用计费与幂等规则，不能简单复制旧任务。
- `cancel` 需要区分 queued、running、provider already started 三种情况。

验收标准：

- 用户能在一个页面看到所有运行中、失败、完成任务。
- 每个失败任务都有明确下一步。
- 任务详情能展示关联资产、关联项目、扣费状态。
- 重试和取消不会造成重复扣费、孤儿资产或状态不一致。

### 2.2 计费生命周期收口

已确认：

- `packages/billing/src/policy.ts` 中已有 billing surface。
- `apps/server/src/services/billing-ledger.ts` 有 `reserveAndTrack`、`debitReservedAndTrack`、`refundReservedAndTrack`。
- 当前策略中 `workspace.generate` 和 `openai.gateway.chat` 是 credit-ledger。
- 当前策略中 `canvas.pipeline.beta` 是 free，`subtitle.asr.beta` 是 cost-only。

问题：

Canvas 和 Subtitle 都可能产生成本。如果长期保持 free 或 cost-only，产品会出现“用户无感消耗成本”的风险。更重要的是，任务失败、取消、部分成功、重试时的计费解释不完整。

建议先补齐一张“计费生命周期表”，再改代码：

| 业务场景 | 当前建议状态 | 是否进入余额账本 | 说明 |
|---|---|---|---|
| 普通文本生成 | 保持 credit-ledger | 是 | 已接近标准闭环 |
| 普通图片生成 | 保持 credit-ledger | 是 | 需要确认实际输出成本 |
| 普通视频生成 | 保持 credit-ledger | 是 | 高成本，必须严格 reserve |
| Gateway Chat | 保持 credit-ledger | 是 | API 用户需要稳定账单 |
| Canvas 分析/拆解 | 可先 free quota | 可选 | 可作为引导额度，但要限流 |
| Canvas 视频生成 | 改为 credit-ledger | 是 | 高成本阶段，必须扣费 |
| Canvas 合成/后处理 | 固定价或 cost-only | 待定 | 如果本地算力成本低，可后置 |
| Subtitle ASR | 改为 credit-ledger | 是 | 按时长/模型计费 |
| Subtitle burn | 固定价或 cost-only | 待定 | 视机器成本决定 |

建议计费状态：

```text
none
estimated
reserved
debited
refunded
partially_refunded
failed_without_charge
manual_adjusted
```

任务事件与计费动作建议：

| 任务事件 | 计费动作 |
|---|---|
| 创建草稿 | estimate |
| 接受执行 | reserve |
| provider 成功返回 | debit |
| provider 未开始前失败 | refund |
| provider 已开始但失败 | 按供应商成本策略 debit/refund |
| 用户取消 queued | refund |
| 用户取消 running | 根据 provider 是否已开始处理 |
| 管理员补偿 | manual_adjusted |

验收标准：

- 每一笔扣费都能追溯到任务或 generation record。
- 每一个任务都能解释当前费用状态。
- 失败、取消、重试都有测试覆盖。
- 管理员调账必须有原因、操作者、时间和审计日志。

### 2.3 幂等与重复提交防护

问题：

AI 生成接口通常耗时长、成本高，用户双击、浏览器重试、API 客户端超时重发都可能导致重复任务和重复扣费。

建议：

所有创建型高成本接口支持 `Idempotency-Key`：

```text
POST /api/generate
POST /api/canvas/:id/run
POST /api/subtitle
POST /v1/chat/completions
```

建议数据表：

```text
idempotency_keys
- account_id
- key
- route
- request_hash
- response_status
- response_body
- task_id
- generation_record_id
- expires_at
- created_at
- updated_at
```

规则：

- 同一账号、同一路由、同 key、同 request hash：返回第一次请求结果。
- 同 key 但 request hash 不同：返回 409。
- 第一次请求已创建任务但未完成：返回 task id 与当前状态。
- 第一次请求已完成：返回最终结果或目标资源。
- 幂等记录需要过期策略，避免表无限增长。

验收标准：

- 同一个创建请求重复提交 10 次，只创建一个任务。
- 重试请求不会重复 reserve。
- API 客户端超时后重试能拿到原任务状态。

### 2.4 错误分类与用户可恢复动作

问题：

系统错误、供应商错误、参数错误、余额错误、内容安全错误对用户的意义不同。如果只展示“生成失败”，产品会显得不可控。

建议统一错误模型：

```ts
interface ProductError {
  code: string
  category: 'validation' | 'billing' | 'provider' | 'storage' | 'rate_limit' | 'content_policy' | 'system'
  message: string
  retryable: boolean
  userAction: 'edit_input' | 'retry' | 'recharge' | 'wait' | 'contact_support' | 'none'
  supportCode: string
}
```

建议映射：

| 错误类别 | 用户动作 | 是否重试 |
|---|---|---|
| 参数错误 | 修改输入 | 否 |
| 余额不足 | 充值 | 否 |
| Provider 超时 | 稍后重试 | 是 |
| Provider 限流 | 等待或换模型 | 是 |
| 存储失败 | 系统自动重试 | 是 |
| 内容安全 | 修改内容 | 否 |
| 系统未知错误 | 联系支持 | 视情况 |

验收标准：

- 任务详情、toast、通知、管理端看到的是同一套错误 code。
- 用户知道下一步做什么。
- 管理员能用 supportCode 定位日志。

问题：

- 管理端能记录处理人、处理时间和处理结果。

## 6. 数据一致性与补偿

重点风险：

| 场景 | 风险 |
|---|---|
| reserve 成功但任务创建失败 | 用户余额被占用 |
| provider 成功但资产保存失败 | 用户被扣费但拿不到结果 |
| 任务成功但 generation record 未更新 | 前端看不到结果 |
| 用户取消时 provider 已经开始执行 | 退款策略不清 |
| SSE 丢事件且轮询失败 | 用户不知道任务完成 |
| 对象存储删除失败 | DB 已删但文件仍存在 |

建议新增或整理周期性 reconciler：

```text
billing-reconciler
generation-record-reconciler
asset-storage-reconciler
task-orphan-reconciler
provider-health-reconciler
notification-reconciler
```

每个 reconciler 需要输出：

- 扫描数量
- 修复数量
- 跳过数量
- 失败数量
- 需要人工处理数量

验收标准：

- 能发现孤儿 reserved credits。
- 能发现“扣费成功但无资产”的异常。
- 管理端能看到需要人工处理的异常项。

## 7. 测试补齐

### 7.1 领域闭环测试

必须覆盖：

```text
创建生成 → reserve → task queued → worker success → debit → asset ready → notification
创建生成 → reserve → provider fail → refund → notification
创建生成 → insufficient balance → no task → notification
取消 queued task → refund
重试 failed task → 不重复扣费
```

### 7.2 API contract 测试

覆盖：

- 用户任务 DTO。
- 统一错误格式。
- `Idempotency-Key`。
- API Key scope denied。
- Rate limit。

### 7.3 管理端能力测试

覆盖：

- 管理员重试任务。
- 管理员取消任务。
- 管理员人工调账。
- 非管理员访问被拒绝。
- 敏感操作写入审计日志。

## 8. 推荐实施顺序

### Sprint 1：任务中心与错误恢复

## 9. 最高优先级清单

如果只选 10 个马上进入排期：

1. 用户侧统一任务 DTO 与任务列表。
2. 任务详情展示费用、资产、错误和下一步动作。

10. Billing reconciler。

## 10. 暂不优先

这些能力重要，但不建议抢在功能闭环之前：

- 完整企业团队协作。
- 大规模模板市场。
- 高级 BI 报表。
- 多语言国际化。
- 私有化部署。
- 插件生态。
- 复杂前端动效。

先把任务、计费、失败恢复、查账、资产复用和后台排障做好，产品才具备投放和运营的底座。
