# 测试覆盖率风险分析报告（快照）

> **性质**：这是一次覆盖率快照 + 风险分析，不是 CI 覆盖率门槛。原则是**合理测试优先，不追求 100%**——纯规则包覆盖率高是架构的自然结果，db 集成测试不进覆盖率数字不代表"没测"，FFmpeg CLI 包装和 shadcn UI 基础组件为了数字补测是低 ROI 投入。
>
> 快照时间：2026-06-14
> 运行环境：本地 macOS（docker compose PG 已启动）
> 测试总数：839（bun，--isolate）+ 73（db 集成，PG）+ 148（client vitest）= 1060，全部通过
> 整体函数覆盖率：66.5% / 行覆盖率：75.9%（bun 全量）

本报告的目标不是「把数字推到 100%」，而是定位真正值得投入测试的盲区，避免在低 ROI 的地方浪费时间。

## 一、覆盖率是怎么跑出来的

```bash
# 服务端 + 所有 packages（必须用 --isolate，否则 mock.module 互相污染）
bun test --isolate --coverage

# 数据库集成测试（需要 PG）
cd packages/db && bun run test:db

# 客户端（需要先安装 @vitest/coverage-v8）
cd apps/client && bun run test -- --coverage
```

三个数字互相独立，**没有任何一次运行覆盖全部代码**——这点决定了下文每一段的解读方式。

### 3.2 数字偏低但其实健康的包

#### `packages/db`（行 61.7%）

**表象误导。** `packages/db/test/` 下有 73 个 PG 集成测试，覆盖：

- `accounts.repo.test.ts`
- `canvas-repos.test.ts`
- `credit-repo.test.ts`
- `generation-records.repo.test.ts`
- `uploaded-files.repo.test.ts`

全部通过。但 `bun test` 默认跳过需要 PG 的测试（没有 PG 就报错），所以覆盖率报告把这些仓库算成 0%。**真实覆盖率远高于报告数字。**

如果想要把 db 也纳入覆盖率统计，需要写一个聚合脚本：

```bash
# 假想的聚合方式（未实现）
DATABASE_URL=postgres://... bun test --isolate --coverage packages/db
```

当前没有必要做这件事，db 集成测试已经足够。

#### `packages/provider`（行 87.1%）

`DashScopeClient` 是外部 API 的薄包装，剩下的错误映射、模型映射部分已覆盖到位。**不需要 mock 整个 DashScope**——mock 会很脆，每次 API 改动都要重写。

#### `packages/storage`（行 85.0%）

OSS 包装同理，IO 重，剩余缺口在异常路径上，单元测试价值低。

### 3.3 真正值得追加测试的盲区（按 ROI 排序）

#### `packages/provider/src/model-validator.ts`（1.5% 行）

173 行纯函数验证逻辑，无 IO。新模型上线时这是高风险区（schema 错配会静默失败）。**最该补**。

#### `packages/provider/src/model-configs.ts`（0% 函数 / 99.56% 行）

大部分是声明式配置（不需要测），但其中若干 helper 函数（如 mapping 归一化）0% 覆盖。每次加新模型都会经过这里。

#### `apps/server/src/modules/generation/output-parser.ts`（28% 行）

解析 DashScope 返回 → 写入 `generation_records`。**直接影响 billing 与 SSE 推送**，字段错配会静默扣费或前端永远显示 processing。

#### `apps/server/src/routes/subtitle.ts`（59% 行）

字幕流水线状态机，错误路径（ASR 失败、burn 失败、export 超时）覆盖薄弱。这条链路有 4 个独立轮询，每个错误分支都有用户可见后果。

#### `apps/server/src/modules/canvas/*`（多个文件 0% – 7%）

包括 `regenerate.ts` / `videos.ts` / `references.ts` / `storyboard.ts` / `characters.ts` / `locations.ts` / `analysis.ts` / `continuity-rebuild.ts` / `service-crud.ts` / `service-helpers.ts`。

这些是 **canvas 管道阶段处理器**，由 worker 调用而非 server 路由调用。worker 测试可能间接覆盖，但缺乏针对性测试。**pipeline 改造时回归风险高**，建议加 helper 级单测（不依赖 route 层 mock）。

#### `apps/client/src/api/client.ts`（9.3% 行）

Eden treaty 包装 + `unwrapEden` 错误处理（401/403 自动清理 token、抛出结构化错误）。客户端容错核心，目前几乎没测。token 失效回退到登录页这种关键路径如果回归，用户会卡死。

#### `apps/client/src/stores/workspace.ts` 和 `generation.ts`（4% – 22%）

Zustand store 承载生成任务提交的全部状态。未测分支：参数校验失败、模型切换副作用、并发提交冲突。这些 bug 上线后只能等用户反馈。

## 四、不建议追加测试（低 ROI）

| 文件 / 目录 | 原因 |
|---|---|
| `packages/ffmpeg/audio-extractor.ts`、`subtitle-burner.ts` | 纯 ffmpeg CLI 包装。mock 后只剩一行调用断言，端到端验证更有效。|
| `packages/provider/dashscope-client.ts` | mock 完整 DashScope 行为极脆，保留 smoke 测试即可。|
| `apps/client/src/components/ui/*` | shadcn 标准组件，已经 85% – 100%。|
| `apps/client/src/components/canvas/*` | 大部分是 React 视图层，逻辑都在 store / lib 里。先把 lib 测全再说。|

## 五、工程层面建议

### 5.1 根 `test` script 默认改为 `--isolate`

当前根 `package.json`：

```jsonc
"test": "concurrently \"bun run --cwd apps/server test\" ..."
```

`apps/server/test` 已经默认 isolate，但顶层直接跑 `bun test` 不带 isolate 时，会因为 `mock.module` 互相污染出现 224 个假失败（实际全过）。CLAUDE.md 有提示这一点，但默认脚本仍然不安全。

**建议**改为：

```jsonc
"test": "bun test --isolate ...",
"test:fast": "bun test ..."   // 单文件时快
```

CI 已用 `test:isolate` 跑了，所以主分支无碍，但本地新开发者第一次跑测试看到 224 个红叉会以为是自己的改动出问题——这是体验问题。

### 5.2 db 集成测试不进覆盖率报告

如前所述，`packages/db/test/` 的 73 个 PG 测试当前不计入任何覆盖率数字。如果未来要做覆盖率门槛（例如 CI gate），需要先解决这个问题，否则 db 仓库会被误判为 0%。

简单方案：另起一个 `test:coverage:db` 脚本，单独跑 db 并输出独立报告。

### 5.3 client `@vitest/coverage-v8`

已补齐到 `apps/client/package.json` devDependencies，可以直接运行 `bun run --cwd apps/client test -- --coverage`。

## 六、优先级建议

如果只能挑 3 件事做：

1. **补 `output-parser.ts` 测试**——影响 billing 正确性，回归代价高，2-3 小时即可写一组 happy/sad path 测试。
2. **补 `model-validator.ts` 测试**——纯函数，1-2 小时写完，下次加模型时立刻能用上做安全网。
3. **根 `test` script 改为 `--isolate`**——一行改动，消除本地假失败。

**其他维持现状即可。** 客户端 stores、ffmpeg、provider IO 层都不建议追加测试，边际收益太低。

## 七、后续补测顺序（执行建议）

按影响面和回归代价排序，只补真正能防回归的边界：

1. **`output-parser.ts`**：影响生成结果、billing 与 SSE 回显。回归代价高，纯函数易测。
2. **`model-validator.ts`**：影响新模型接入与 provider 参数安全。纯函数，下次加模型时立刻能用做安全网。
3. **canvas 阶段 helper**：影响自动执行链路稳定性。建议加 helper 级单测，不依赖 route 层 mock。
4. **Eden `unwrapEden` / auth 失效处理**：影响登录态恢复与错误提示。客户端容错核心。

后续任务仍以 `docs/TODO.md` 为准，本报告不创造新的长期任务源。
